# CardGame DI V2 设计规格

**状态：** 已实施，终审修订版
**日期：** 2026-08-10
**功能：** feat-002 Pure C# DI Boundary
**适用范围：** 仅服务 CardGame，不作为通用包发布

## 1. 背景与目标

旧根目录 `DI/DIContainer.cs` 同时承担注册、解析和 Unity 对象判断，导致核心容器直接依赖 `UnityEngine.Object`，也没有可靠的程序集边界、不可变构建模型和层级作用域验证。CardGame 后续的单局、遭遇、地图、叙事和伤害结算都需要稳定的对象生命周期，因此本阶段以可维护性优先，允许替换旧 API，而不是兼容有风险的旧实现。

本设计的目标是：

- 在 `Assets/Plugins/RazorFramework/DI/` 建立不引用 Unity 的纯 C# 容器；
- 注册只在 `ContainerBuilder` 中发生，成功 `Build()` 后模型不可变；
- 明确定义 Singleton、层级 Scoped、Transient 的解析、所有权和释放；
- 在构建时发现重复注册、非法构造函数、缺失依赖、依赖环和生命周期错误；
- 用结构化错误保留服务、实现和依赖链上下文；
- 把 Unity 对象成员注入隔离到 `RazorFramework.Unity.DI`；
- 通过 Unity 初始化阶段捕获的可信主线程身份，使注入器在未初始化或工作线程上 fail-closed；
- 用 Node Harness 与 Unity EditMode 测试共同守住边界。

## 2. 非目标

本阶段不做以下工作：

- 不保持旧 `DIContainer` 的 API 兼容；
- 不实现开放泛型、属性自动扫描、子容器覆盖注册或运行时注册；
- 不把 `IServiceResolver` 当作玩法层的通用 Service Locator；
- 不迁移 `Boot`、`Events`、`Input`、`Lifecycle`、`MVVM`；
- 不实现卡牌、伤害结算、地图、剧情、存档、文案或数值系统；
- 不宣称已完成 IL2CPP、托管代码剥离、AOT 或目标平台验证。

## 3. 程序集与依赖边界

```text
RazorFramework.DI
  └─ BCL only

RazorFramework.Unity.DI
  ├─ RazorFramework.DI
  └─ UnityEngine

RazorFramework.DI.Tests
  └─ RazorFramework.DI

RazorFramework.Unity.DI.Tests
  ├─ RazorFramework.DI
  └─ RazorFramework.Unity.DI
```

`RazorFramework.DI.asmdef` 的固定契约为：

```json
{
  "name": "RazorFramework.DI",
  "rootNamespace": "RazorFramework.DI",
  "references": [],
  "autoReferenced": true,
  "noEngineReferences": true
}
```

`autoReferenced: true` 是当前明确决策：CardGame 的后续程序集可以在创建专用 asmdef 前发现 DI 核心。它不是永久最佳值；若 feat-003 改为显式引用，必须先修改规格、测试和 Harness，再改变字段。

Unity 适配器 `autoReferenced: false`，只允许显式引用，防止反射注入无意进入不需要它的程序集。

## 5. 注册与不可变构建

核心入口为 `ContainerBuilder`：

```csharp
var builder = new ContainerBuilder();
builder.DefineScope<RunScope>();
builder.DefineScope<EncounterScope, RunScope>();

builder.AddSingleton<IClock, GameClock>();
builder.AddScoped<RunState, RunScope>();
builder.AddScoped<BattleContext, EncounterScope>();
builder.AddTransient<DamagePreviewService>();

using var container = builder.Build();
```

约束如下：

- 默认注册每个服务类型只能有一个；集合注册使用独立入口并保持显式顺序；
- 外部实例通过 `AddSingleton(instance)` 注册，所有权仍属于调用方；
- `Build()` 成功后 builder 被消费，再次注册或构建均失败；
- 构建失败不消费 builder，调用方可修正后重试；
- 构建模型复制注册与作用域数据，不向运行时暴露可变注册表；
- 默认解析只按精确服务类型匹配，不做隐式 assignable 搜索。

## 6. 构造函数与依赖图

实现类型必须是可赋值、非抽象、非接口、闭合的具体类型。构造函数规则：

- 只有一个 public 构造函数时直接选用；
- 多个 public 构造函数时，必须且只能有一个标记 `[InjectConstructor]`；
- 非 public 构造函数即使标记也不接受；
- 缺失依赖和间接依赖环在 `Build()` 时失败；
- `IReadOnlyList<T>` 只从显式集合注册解析；无集合条目时注入空只读数组。

验证错误使用 `DependencyInjectionException`，至少包含：

- `Code`：稳定的 `DependencyErrorCode`；
- `ServiceType`：失败服务；
- `ImplementationType`：相关实现；
- `DependencyPath`：从消费者到失败依赖的实现类型链；
- `InnerException`：构造函数真实异常。

对于兄弟作用域冲突，单条线性链无法表达分叉，因此路径采用“消费者、左侧要求链、右侧要求链”的稳定顺序。例如：

```text
NeedsBattleAndShop -> BattleState -> ShopState
```

这表示同一消费者同时需要互不兼容的两个 scope，不把它误述为 BattleState 依赖 ShopState。

## 7. 生命周期与层级作用域

作用域用 marker 类型定义：

```csharp
builder.DefineScope<RunScope>();
builder.DefineScope<EncounterScope, RunScope>();
```

创建规则：

- 根容器只能创建无父级的 scope；
- `ServiceScope` 只能创建其声明的直接子 scope；
- 子 scope 可以解析祖先 scope 服务；
- 父 scope、兄弟 scope 或根容器不能解析不可见的 scoped 服务。

生命周期语义：

| 生命周期 | 缓存与归属 | 允许依赖 |
|---|---|---|
| Singleton | 根容器缓存并持有 | Singleton、外部实例、无 scoped 要求的 Transient |
| Scoped | 声明 scope 的实例缓存并持有 | 可见祖先或同级 scope，以及合法 Transient |
| Transient | 每次创建，由发起解析的根容器或 scope 持有 | 当前活动 scope 可满足的依赖 |

构建期会传播每个注册的“最严格所需 scope + 依赖路径”：

- Singleton 间接捕获 Scoped 时抛 `CaptiveDependency`；
- Scoped 依赖其后代 scope 时抛 `CaptiveDependency`；
- 同一服务要求兄弟 scope 时抛 `ScopeMismatch`；
- 集合条目参与同样的传播与冲突检查；
- 运行时缺失活动 scope 时复用构建模型中的精确路径。

## 8. 并发、所有权与释放

- Singleton 和 Scoped 使用线程安全的惰性初始化，同一 owner 内并发解析只构造一次；
- 容器创建的 Singleton、Scoped 和 Transient 都由对应 owner 记录；
- 外部实例不由容器释放；
- 子 scope 先于父 scope 释放；同一 owner 内按实例创建逆序释放；
- 一个 `Dispose()` 抛错不阻止后续对象释放，最终以 `AggregateException` 汇总；
- 已释放容器或 scope 的解析抛 `ContainerDisposed`；
- 本阶段只支持同步 `IDisposable`，不支持 `IAsyncDisposable`。

## 9. 解析 API 与诊断

`IServiceResolver` 提供：

```csharp
object Resolve(Type serviceType);
T Resolve<T>() where T : class;
bool TryResolve(Type serviceType, out object service);
IReadOnlyList<T> ResolveAll<T>() where T : class;
```

`Resolve` 用于必需依赖，未注册即结构化失败；`TryResolve` 只把“未注册”转换为 `false`，不会吞掉构造、scope 或释放错误。业务对象优先使用构造函数依赖；resolver 只放在框架边界、工厂或 Unity 适配器。

`ContainerOptions.DiagnosticSink` 可观察容器构建、scope 创建、实例创建、解析失败、scope 释放和容器释放。诊断回调是观察性通道，其自身异常被隔离，不改变容器行为。

## 10. Unity 对象成员注入

`UnityObjectInjector` 只处理 `UnityEngine.Object` 的字段/属性注入：

```csharp
public sealed class BattleView : MonoBehaviour
{
    [Inject] private BattlePresenter _presenter;
    [InjectOptional] public ICombatTelemetry Telemetry { get; private set; }
}
```

规则：

- `[Inject]` 是必需依赖，未注册时抛 `MissingDependency`；
- `[InjectOptional]` 未注册时跳过；
- 只能标记可变实例字段，或有 setter 的非索引实例属性；
- 静态、readonly、const、索引、无 setter、双重标记成员均抛 `InvalidMember`；
- 计划按基类到派生类、同一声明类型内 `MetadataToken` 顺序执行并缓存；
- 赋值失败包装为 `AssignmentFailed` 并保留 `InnerException`；
- 在任何 Unity null 比较或 `GetType()` 前先检查可信主线程。

### 可信主线程守卫

`UnityMainThread` 在 `RuntimeInitializeLoadType.SubsystemRegistration` 清空旧状态，并在 `BeforeSceneLoad` 捕获当前 Unity 主线程的托管线程 ID。`UnityObjectInjector` 构造和每次 `Inject` 都执行同一检查：

- 尚未由 Unity 运行时初始化时拒绝；
- 在工作线程构造时拒绝，即使之后仍在该工作线程调用；
- 在主线程构造、工作线程调用时拒绝；
- 检查失败统一抛 `WrongThread`；
- 测试初始化钩子为 `internal`，只通过 `InternalsVisibleTo` 对 EditMode 测试程序集开放，不增加生产 public API。

因此注入器不是线程调度器。生产代码应在 Unity 初始化完成后、主线程上创建和调用它。

## 11. Harness 契约

便携 Harness 必须验证：

- DI 核心的命名空间只属于 `RazorFramework.DI`；
- 实际 C# 代码中不存在 Unity import 或限定名；
- 扫描能识别 `UnityEngine . Object`、`global :: UnityEngine . Object`、分隔符附近注释，以及插值表达式，同时不误报普通注释和字符串；
- asmdef 的 `name`、`rootNamespace`、`references`、`autoReferenced`、`noEngineReferences` 与本规格一致；
- 根 `DI/` 下递归不存在任何 `.cs`；
- 本规格与实施计划不包含连续大量 `?`、重复 Unicode replacement character，且保有最低中文内容；正常中文问号不误报；
- 工作树 whitespace 检查通过。

完整 Harness 在此基础上调用 Unity `6000.3.10f1` EditMode 测试，并严格验证新生成的 XML 结果。

## 12. 验收条件

- 纯 C# Core 在 asmdef 和 Harness 两层都拒绝 Unity 引用；
- builder 冻结、依赖图、层级 scope、集合、并发、所有权和逆序释放均有 EditMode 覆盖；
- `CaptiveDependency`、兄弟 scope 冲突与运行时 `ScopeMismatch` 提供可用 `DependencyPath`；
- Unity 注入器绑定 Unity 初始化阶段捕获的主线程，不接受任意构造线程；
- destroyed object 在正确线程上仍为 no-op，错误线程先于 Unity null 访问失败；
- 旧根 DI 源码删除且换名/嵌套形式会被 Harness 拒绝；
- Node、便携 Harness、完整 Unity Harness 和 `git diff --check <base>..HEAD` 通过；
- README、Harness 指南、架构审查、功能证据、进度和交接均反映真实行为。

## 13. 已知限制

- 反射成员注入只在 Editor EditMode 验证；IL2CPP、linker stripping、AOT 和目标平台构建未验证；
- 当前没有 `link.xml` 或生成式注入代码；发布前必须补保留策略和目标平台构建，或改用显式/生成式注入；
- 线程身份依赖 Unity runtime initialization callback，不提供跨线程调度；
- DI V2 完成不代表旧框架其他模块已可用于 CardGame；其历史风险保存在 `docs/legacy-framework-audit.md`，需在 feat-003 重新核对。
